# ADR-013：Gate D 跨进程证据重授权模型

- **状态**：草案
- **日期**：2026-08-19
- **决策 owner**：LocalCAT 项目 owner
- **关联 Spec**：`tm-storage-retrieval-index` Requirement 8；`feature5-ui-integration` Requirement 6 / Task 3.6 / Qt TM surfaces

## 背景

当前 Qt composition 在每个进程中重新执行 Matcher Gate → Gate C → Gate D。Gate D 为两条 intended path 运行 literal oracle 与 100,000-record migration/query/latency；本机 current-source 实测约 540.5 秒。主线程未被阻塞，但 FUZZY 在整个窗口内必须关闭。

仓库已跟踪与当前 implementation fingerprint 匹配的 `benchmark_tm_evidence.json`，但现有发布协议只接受本进程 Core owner 在新 absent evidence path 上完成真实运行后铸造的一次性 receipt。严格 codec、digest 和 implementation fingerprint 能证明 bundle 内部一致，不能单独证明它由某次受信真实执行产生。

## 待批准决策

本记录收束为“同设备持久资格 + 显式手动同步”的 ADR candidate；在正式采纳和协议闭合前仍保持现有 per-process Gate D：

1. Gate D 的资格作用域是设备与 retrieval implementation epoch，不是项目或某一份 TM。项目/TM 内容未变、Lookup/Update 配置改变，均不能单独铸造或撤销 Gate D 资格。
2. 采纳后，应用启动不得自动实跑 Gate D。若没有可验证的本设备 attestation，或 compatibility key 已失配，Exact/Context 保持各自当前能力，FUZZY fail-closed；UI 提供显式“同步 Fuzzy 性能资格”操作。
3. “同步”必须由当前进程 Core owner 真正运行既有 Gate D oracle/100k intended paths，并在成功 publication 的同一事务尾部铸造设备本地 attestation；它不是导入、复制或信任 tracked `benchmark_tm_evidence.json`。
4. 后续进程只能由 Core 验证并重授权该 attestation。Qt、Controller 和 application cache 不得解析 bundle 后自行开放 FUZZY，也不得从 `RUNNING/SUCCEEDED` 展示状态推断 capability。
5. compatibility key 至少绑定 device identity、implementation fingerprint、benchmark/proof version、Gate C build/semantics/fixture/evaluator identity、Python/SQLite/Unicode/platform 与 intended-path identity。任一字段不匹配、attestation 损坏/缺失/篡改，只关闭 FUZZY，不撤销 exact/context。
6. 实现 amendment 必须在采纳前冻结 device-local provenance、密钥/签名或等价防伪边界、有效期、原子写入、并发 singleflight、手动重新同步、损坏恢复和 cleanup；普通 JSON digest 或 implementation fingerprint 本身不构成 provenance。
7. 在候选待决期间，UI 可以非授权地显示 `Gate D RUNNING/FAILED`，但当前 per-process 自动运行与 receipt 协议不变。

## 长期约束

- Gate C fuzzy-core 与 Gate D intended-path 资格继续是独立 authority；缓存只能优化 Gate D 证明生命周期，不能替代 Gate C。
- FUZZY 只在 Core 对完整兼容性和 provenance 复证后才可发布；缓存损坏或失效只能 fail closed。
- Qt 只消费 Controller 安全投影，不得依赖 benchmark/evidence/receipt 实现。
- 新协议必须保留旧在途 query 的 immutable snapshot 和 Gate C/D publication 原子性。

## 后果与权衡

候选可取消每次冷启动约九分钟的自动等待，并保留“当前设备确实完成性能硬门”的原语义。代价是首次或 compatibility key 失效后，FUZZY 会保持关闭直至用户显式同步；同时必须引入可信的 device-local provenance 与持久化恢复协议。

## 备选方案

- **继续每进程重跑**：当前已授权的基线，安全但产品等待过长。
- **发布流程签发、所有设备直接复用**：本候选不采用。它不能证明当前设备满足既有性能硬门，若未来需要必须另行取代本决策。
- **直接复用 tracked `benchmark_tm_evidence.json`**：被拒绝。它缺少可重铸 receipt 的 provenance，并违反当前 frozen protocol。
- **只按 digest/fingerprint 信任 application cache**：被拒绝。内部自洽不是真实执行证明。
- **只改 UI 文案**：可作为独立的无 ADR 短期补救，但不解决冷启动耗时。

## 取代关系

- **取代**：若采纳跨进程复用，将精确取代 `feature5-ui-integration` Design 187–188 / Research 44 的 per-process no-cache 约束；ADR-009/011 的 Core authority 与 Layer 4 边界保留。
- **被取代于**：None
