# ADR-015：Parser/Codec 中立边界、用途感知选择与能力式扩展

- **状态**：已采纳
- **日期**：2026-08-20
- **决策 owner**：LocalCAT 项目 owner
- **关联 Spec**：`parser-subsystem-extraction`

## 背景

ADR-004 要求 `Parser → Engine`，并允许 Parser 导入 Engine 数据模型；ADR-005 要求所有解析器继承 `BaseParser`，且 Registry 只接受其子类。当前路线图、技术 Steering 与 Parser rebaseline 已发现这两个机制不再适合当前系统：

- Parser 与 Engine 应当互相独立，由 Application/adapter 同时组合两者；
- `.json` 可以同时表示项目文档和 normalized TM resource，扩展名不能成为用途权威；
- Reader、canonical writer、source-preserving round-trip writer 与 language-resource import 是不同能力，不能由一个强制基类推导；外部格式的 tokenization、sidecar 和写回也不能变成 LocalCAT Core 的职责；
- Parser 产生单输入的中立记录，多文档 workspace 才拥有 Project/Document 聚合、稳定复合身份与保存调和。

项目 owner 于 2026-08-21 明确采纳本 ADR。该采纳授权 Parser Design 使用以下边界，但 Parser runtime 仍须等待 Requirements、Design、Tasks 三阶段全部批准。

## 决策

1. **依赖方向**：Parser 与 Engine 不得互相 import。Application/adapter 可以同时依赖两者，并将中立 parsed records 映射为 `EditorProject` 或 TM/termbase owner 批准的输入契约。若确需共用 primitive，必须放在双方都不拥有的中立契约边界。
2. **扩展合同**：统一性来自版本化行为契约和显式 capability，不来自强制 nominal inheritance。当前生产代码不存在 `BaseParser` 或依赖它的真实 consumer，因此本轮不新建 `BaseParser` compatibility façade，Registry 也不得以名义继承作为注册门。既有 `editor_project.py`、`resource_importer.py`、CLI 和 runner 等 Application façade 可以保留公开返回形状与稳定错误映射，但必须委托唯一 codec 语法权威。
3. **用途感知选择**：调用方必须显式提供三个闭合 effective purpose 之一：`project_document`、`language_resource.translation_memory`、`language_resource.termbase`。Registry 权威键至少为 `(effective_purpose, format_id)`；extension/MIME/sniff 只产生发现候选，不取代 effective purpose。重复权威键必须拒绝，不得 last-registered-wins。首波稳定 Format ID 为 `localcat-json-v1`、`line-text-v1`、`gettext-po-v1`、`gettext-pot-v1`、`tmx-level1-v1`、`normalized-tm-json-v1`、`termbase-csv-v1`、`termbase-xlsx-v1`，不由 Registry 自行发明。
4. **结果、Plugin 防腐层与聚合**：Parser Foundation 产生单输入的 `ParsedDocument` 或中立 language-resource records，并提供格式中立的 plugin port、opaque capability 与 terminal outcome。独立外部格式规格通过可配置 Format_Codec_Plugin 在仓库边界形成 DDD 防腐层；例如 `rpy-project-codec` 自己拥有 RPY tokenization、sidecar、占位符保护、可选回填/导出和 round-trip 验证，LocalCAT Core 不导入 RPY 类型、不解释 token，也不直接写 `.rpy`。单输入 plugin 不必等待多文档 UI；`multi-document-project-workspace` 才拥有多个输入的 `ProjectDocument`、显示顺序、dirty/reconciliation、复合 segment identity 和多文档保存报告。
5. **iterator terminal**：流式 records 在 terminal success 前均为 provisional。fatal、limit-exceeded、cancel、consumer exception 或 early close 都不得授权 commit；Application 必须先 stage，只在唯一 terminal success 后提交。
6. **Writer 与 token**：Reader 不暗示 Writer；`canonical_write` 与 `source_round_trip_write` 是不同 capability。外部格式的 Writer、回填和导出由对应 plugin/ACL 拥有，不属于 LocalCAT Core。格式私有 token 对 Core/workspace/UI opaque，并绑定 plugin identity/version、source fingerprint 和格式状态；任一 identity 失配必须在首次 mutation 前失败。
7. **语言资源边界**：Parser/codec 不拥有 TMStore、SQLite、去重、排序、canonical activation 或术语事务。TMX 只能作为 `language_resource/translation_memory`，不得注册为 `project_document`。

## 长期约束

- 新 codec 不得要求修改 Engine 才能注册。
- Parser 合同不得暴露 Qt、Controller、TMStore、SQLite 或 workspace ProjectDocument 类型。
- Format_Codec_Plugin 缺失、禁用或版本不兼容时必须返回 unsupported capability；LocalCAT Core 不得提供猜测性内建 fallback。
- compatibility façade 只能委托唯一新 authority，不得保留平行语法实现。
- 未由 codec/plugin 显式声明的 Reader/Writer/round-trip capability 必须在操作前 fail closed。

## 后果与权衡

Parser 可以在不污染 Engine/Store/workspace authority 的前提下支持同扩展名的不同用途，并让外部格式通过 DDD 防腐层提供可选 Writer，也能对流式 fatal/abort 提供可提交性边界。代价是必须引入明确 purpose/capability/terminal/plugin 合同，并让既有 Application 入口通过受测 façade 渐进委托；这些 façade 保护调用形状，不保留第二份 tokenizer、validator 或 row-selection 权威。

## 备选方案

- **继续 Parser → Engine**：拒绝候选。这会让格式边界直接依赖 TM/匹配模型，不利于单文档中立记录和多用途选择。
- **继续强制 BaseParser 继承**：拒绝候选。nominal inheritance 无法诚实表达 Reader-only、canonical writer 和 round-trip writer 的不同能力。
- **仅按扩展名选择**：拒绝。Project JSON 与 normalized TM JSON 会产生权威冲突。
- **Parser 直接提交 TM/术语存储**：拒绝。语法成功不等于 application/store 事务获得授权。

## 取代关系

- **取代**：ADR-004、ADR-005
- **被取代于**：None

ADR-004 保留“Engine 格式无关”的目标，但其 `Parser → Engine` 机制已被取代。ADR-005 保留“调用方拥有统一合同”的目标，但“必须继承 BaseParser / Registry 只接受子类”已被取代。自 2026-08-21 起，以本 ADR 的中立合同、Application 映射和行为/capability 准入为唯一后续约束。
