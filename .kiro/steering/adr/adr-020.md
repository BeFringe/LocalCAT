# ADR-020：跨平台 rooted 文件权威、锁与耐久发布边界

- **状态**：草案
- **实施授权**：`NO-GO`（不批准 scope、实现或发布）
- **日期**：2026-08-25
- **决策 owner**：LocalCAT 项目 owner（待人工审阅）
- **关联 Spec**：`windows-platform-enablement@c3a1080d5e8dbf13c3dde943bd48c033e2105a87`（working label W1）；相邻 `parser-subsystem-extraction`、`collaborative-job-chunks`、`multi-document-project-workspace`、`language-resource-portability`、`tmx-context-interchange`、`tm-storage-retrieval-index`

## 背景

LocalCAT 已在 Parser、协作 chunk、ProjectPackage、资源、TMX 与 TM activation/snapshot/recovery 中采用 rooted open、稳定文件身份、跨进程锁、candidate publish、journal/LKG 与 readback 等 fail-closed 协议，但具体原语分散依赖 POSIX `dir_fd`、`O_NOFOLLOW`、`O_DIRECTORY`、`flock` 和 directory `fsync`。Windows 没有这些接口；删除 `fcntl` import 或以路径规范化、普通 `os.replace`、测试 skip 近似，会改变 authority、原子发布、durability、恢复与 dependency boundary，跨过治理规则第 17、19、20、21 条门槛。

Windows 的 reparse、share mode、live FileId、handle-relative rename、`LockFileEx` 与 naming durability 也不能逐项机械翻译 POSIX。尤其 Windows FileId 删除后可能复用，只能比较同时存活且已验证的 handles；candidate rename 后的 handle/share 生命周期、非合作 writer 威胁和 power-loss 后的成功边界必须成为显式平台合同。

本草案只提出长期平台边界。它不批准 `windows-platform-enablement` scope、相邻 Spec amendment、任一运行时实现或 Windows 发布。

## 决策

本 ADR 若获采纳，作出以下决策：

1. **单一跨平台能力边界**：Parser、Chunk、Project/Resource/TMX 与 TM 业务模块只消费 backend-neutral `RootedFileSystem`、`ProcessFileLock`、bound publisher 与 opaque file identity 合同。依赖方向固定为 `business owner → platform contracts → composed adapter → OS API`；Qt 和业务模块不得直接导入 POSIX/Win32 primitive。
2. **live-handle rooted authority**：root、每个 ancestor 与 final entry 必须由保留的 OS handle 逐组件绑定并复证 containment、kind、link/reparse facts 与 live identity。Windows rooted walk 使用文档化 desktop handle API，拒绝任一 reparse component、namespace/path ambiguity 或 unsupported volume；字符串 `resolve`、prefix compare、CWD 与 pathname hash 只可作诊断，不能铸造 authority。
3. **opaque identity**：平台 identity 只用于比较同时存活的已验证 handles。POSIX 可由 device/inode 表达，Windows 使用 volume serial 与 `FILE_ID_INFO` 的 128-bit FileId；该值不可序列化为跨重启 authority，历史值不能单独批准读取、替换或恢复。
4. **Windows handle profiles**：root/intermediate handle 在 rooted operation 内保留且不共享 write/delete；source handle 允许读但不共享 write/delete；candidate 以 `CREATE_NEW`、无共享和 write-through profile 创建；persistent lock handle 共享 read/write 但不共享 delete。具体 access/share/flag 集合由平台合同精确固定，不得以消除 sharing violation 为由扩大。
5. **自包含的 protocol-control lock profile**：W1 自己拥有 `ProtocolControlLockSecurityV1`，不依赖 W2 的 Windows private-proof capability。persistent lock file 的 owner 必须是当前 process primary token 的 canonical `TokenUser` SID；DACL revision固定为`ACL_REVISION`，authority-relevant control bits必须`SE_DACL_PRESENT|SE_DACL_PROTECTED`且清除`SE_DACL_DEFAULTED|SE_DACL_AUTO_INHERITED|SE_DACL_AUTO_INHERIT_REQ`，representation-only `SE_SELF_RELATIVE`归一化后不参与比较。DACL按canonical order精确包含3个`ACCESS_ALLOWED_ACE_TYPE`且每个`AceFlags == 0`：`TokenUser` canonical SID bytes、`CreateWellKnownSid(WinLocalSystemSid)`所得`S-1-5-18`、`CreateWellKnownSid(WinBuiltinAdministratorsSid)`所得`S-1-5-32-544`；三者mask均为`FILE_ALL_ACCESS`。不得以localized name/account lookup解析well-known principal；null/defaulted DACL、任何其他control/ACE flag、deny/object/callback/inherited/unknown ACE、额外principal、owner或mask差异均使lock capability unavailable。当前standard/elevated TokenUser的`GENERIC_ALL`经file `GENERIC_MAPPING`/`MapGenericMask`后必须获得`FILE_ALL_ACCESS`，同SID的low-integrity/restricted token必须不能取得write/delete。lock file必须single-link、位于已证明的protocol-control root，且不由W2 attestation/device-secret协议携带。
6. **可恢复的首次初始化**：lock载体内容固定为可由resource-family key重算的versioned `ProtocolControlLockPayloadV1`（magic、schema、resource-family digest、byte-range-map digest），不含随机或跨重启FileId。首次creator以`CREATE_NEW`、上述security descriptor和`INIT` share-none profile持有唯一句柄，一次写入完整canonical payload、`FlushFileBuffers`、handle-readback后关闭；loser把sharing violation分类为“初始化进行中”并按调用方bounded policy重试。若creator在任一instruction boundary崩溃，后继只可在root/entry/exact ACL/single-link均复证后取得同一`INIT` share-none独占句柄；bytes必须为空、是expected payload的严格前缀或已经完整匹配，才可truncate/rewrite（或对完整内容补flush）、flush/readback并关闭。未知、超长、非前缀或安全事实漂移的bytes只返回`LOCK_UNAVAILABLE`，不得猜测unlink/replace/修补。两名recoverer由share-none open互斥；完成后都必须重新按普通`LOCK` profile打开并复证，不能把初始化句柄直接提升为业务lease。
7. **跨进程锁**：Windows adapter 使用 `LockFileEx/UnlockFileEx` 对上述已完成初始化复证、persistent、single-link、identity/payload-bound lock file 的固定 byte range 加锁，并由 caller 选择 wait/timeout policy。普通open必须重验exact payload/descriptor/entry identity，并在锁定前对完整payload执行flush/readback；lock文件不unlink/replace。正常释放遵循unlock后close，进程终止只承诺OS eventual release，不承诺公平或零延迟。
8. **两种发布模式**：平台只提供 `CREATE_IF_ABSENT` 与 `REPLACE_UNDER_LOCK`。replace 必须由业务 owner 持有覆盖 destination family 的排他 lease；target snapshot 是 stale/recovery 事实，不是 OS expected-identity CAS。平台不得向上层宣称已排除不遵守该 lease 的同用户 writer。
9. **handle-bound publish lifecycle**：candidate 经 write、content flush 与 owner journal/LKG arm 后，以仍打开的 candidate handle 相对 bound parent rename；随后捕获 final facts、关闭全部 candidate handles，再以不请求 write/delete access 且不共享 write/delete 的 profile reopen destination，验证 identity/digest/readback。这个 retained destination readback handle 必须持续到业务 owner 完成 durable state-machine commit 和 terminal reproof 后才关闭；在此之前不能重新打开带 write/delete access 的 destination，也不能把 publish 报告为成功。rename 后结果不明、close/reopen/readback/owner commit/terminal reproof 不闭合时返回 recovery-required facts，不猜测删除 residue 或回退到 copy-over/in-place write。
10. **release-owned `DurabilityProfile`**：Windows release owner 维护版本化、content-addressed、fail-closed 的 `DurabilityProfile`，固定获批的 Windows build/patch family、storage bus/media class、volume locality/NTFS facts、device/OS write-cache 与 flush/write-through 行为、volatile-cache 情况和硬件 power-protection facts。runtime self-probe 必须得到与某一 profile 完全匹配的事实，且该 profile 必须绑定同一事实族上的真实 forced-power-loss/reboot evidence，才能 mint durability capability；只检查 filesystem 名、调用 `FlushFileBuffers` 成功、process-kill/fault-injection 通过或设备自报 write-through 均不充分。profile 或任一事实不能可靠读取、发生漂移或无批准 evidence family 时 fail closed。
11. **耐久成功边界**：Windows 首版仅在 reparse、FileId、lock、handle-relative rename 以及上述 `DurabilityProfile` 全部门成立的本地固定 NTFS volume mint capability。成功必须包含 content flush、获批 write-through/naming sequence、candidate close、destination retained-handle readback、owning state-machine durable commit 与 terminal reproof；未证明 naming durability 或 power-protected persistence 的 host/volume fail closed。
12. **POSIX parity**：现有 `openat`/dirfd/no-follow/flock/directory-fsync 语义迁入 POSIX adapter，不改变业务 success/failure、receipt 或 recovery 输出；同一共享 contract 与 consumer characterization matrix 同时约束 POSIX 和 Windows。
13. **稳定失败族与分权**：平台只返回 capability unavailable、outside-root、reparse rejected、identity stale、lock contended/unavailable、durability unavailable、publish failed 或 recovery required 等稳定低层事实；Win32/POSIX 原始错误与正文/path 不成为 public business error。各 owning Spec 继续拥有业务状态机、journal/LKG、receipt、用户投影与 safe-code mapping。
14. **支持范围与升级门**：首版只接受 Windows 11 desktop、CPython x64 和通过完整能力门的本地固定 NTFS。UNC、remote、ReFS、FAT/exFAT 与 proof 不完整的 volume fail closed；新增 filesystem、改用 native `NtCreateFile`、改变 lock ACL、share mask、identity、publish mode、`DurabilityProfile`、durability success boundary 或 dependency ownership，必须回到 ADR/Spec 治理。

## 长期约束

- authority 由 retained handle、live identity、containment 和 owner-defined content/phase proof 共同组成；路径字符串、可序列化 handle facts、调用方布尔值或 mock capability 都不能替代。
- 上层不能取得 raw Win32 HANDLE 或 dirfd。fault tests 只能经受控 seam 注入，不能绕过 factory self-probe/contract gate。
- 平台 publisher 不拥有 ProjectPackage/TM/Resource/Chunk 的 journal、LKG、generation、receipt 或 recovery 决策，也不把共享低层 primitive 提升为共同业务 authority。
- W1 的 lock-file ACL 只保护 protocol-control integrity，不是 W2 private attestation，不能签发或恢复 Gate D/canonical capability；反向地，W1 lock/authority 也不得依赖 W2，避免平台基础能力循环自证。
- persistent lock载体的首次初始化与creator-crash接管是W1协议的一部分，不是“锁会随进程释放”的自然推论；只有exact empty/strict-prefix/full payload残留可在share-none init handle下恢复，unknown bytes永久保持fail closed直到获批维护动作。
- 不合作 writer 的威胁范围必须保持可见。需要 stronger-than-lease 替换语义的 owner 必须使用获批的 immutable generation/journal/pointer 协议，不得把 pre-snapshot/post-readback 描述为 CAS。
- `DurabilityProfile` 是 release evidence 与 runtime facts 的双向固定合同，不是按 filesystem 名维护的 allowlist；只有同一版本 profile 所绑定的 forced-power-loss evidence family 能支持运行时 mint。
- mandatory Windows safety case 不得通过 skip、path-only fallback、copy-over、现场修补或仅 source-mode evidence 放行。

## 后果与权衡

这项边界让 Windows 和 POSIX 消费者共享同一组可证明的 rooted/lock/publish 语义，消除业务模块中的平台原语复制，也使 Qt source startup 能在 composition 前选择合格 adapter。代价是首个迁移簇较大，Windows 支持范围窄，handle/share 生命周期与 recovery facts 必须严格建模；真实 durability 还需要独立 power-loss lab，而普通单元测试不足以授予支持。

## 备选方案

- **每个业务模块内增加 `sys.platform` 分支**：拒绝。会复制安全逻辑、错误映射和恢复语义，并形成多个平台 authority。
- **`Path.resolve()`/prefix compare + 普通路径 I/O**：拒绝。不能抵抗 reparse、ancestor/final swap 和 TOCTOU。
- **仅删除 `fcntl` 或用 `msvcrt.locking` 代换**：拒绝。不能覆盖 rooted identity、精确 wait/error、publish/durability 与 consumer recovery 合同。
- **以 target snapshot + replace 宣称 CAS**：拒绝。Windows API 不保证不合作 writer 在 snapshot 与 rename 间不能替换目标。
- **首版使用 `NtCreateFile` RootDirectory**：暂不采用。只有文档化 desktop API 不能通过获批反例时，才以新 ADR 评估 native API/ABI 维护成本。
