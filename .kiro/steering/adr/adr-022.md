# ADR-022：Windows frozen onedir/windowed 发行所有权与可信源码闭包

- **状态**：已采纳
- **实施授权**：`NO-GO`（ADR 采纳不等于 owning scope、Design、实现或发布授权；`windows-platform-enablement` 任务 0.2～0.5 尚未闭合）
- **日期**：2026-08-25
- **批准日期**：2026-08-26
- **决策 owner**：LocalCAT 项目 owner
- **关联 Spec**：`windows-platform-enablement@c3a1080d5e8dbf13c3dde943bd48c033e2105a87`（working label W3）；相邻 `feature5-ui-integration`、`qt-editor-json-mvp-increment` 与 Gate/source owning Specs

## 背景

LocalCAT 的 capability host 不把 module import 成功或某个 PASS 布尔值视为授权；它绑定真实 source loader、`__file__`/`spec.origin`/code filename、fixture digest 与 Gate closure。普通 PyInstaller 构建把 pure modules 放入 PYZ，当前 baseline 即使能生成 onedir/windowed 目录，也缺少能力关键真实 `.py`、fixture/data 闭包，因而 frozen startup 正确 fail closed。

ADR-009 拥有 Core evidence/capability authority，ADR-011 拥有 Feature 5 与 UI 的冻结 DTO、composition 和 Controller 边界；二者都没有批准 Windows executable 的 bootstrap trust root、bundle rooted authority、source-only collection、build manifest 或发行 ownership。把 frozen 状态当信任、禁用 Gate、复制一份未执行的 `.py`，或从 CWD/checkout 查找 fixture，都会建立第二 authority 并跨过持久/frozen contract 与长期 ownership 门槛。

本 ADR 建立 Windows frozen distribution 的长期边界。任何 bootstrap、loader、build 或 runtime 实现都依赖 ADR-020 已采纳的 rooted/reparse/live-identity/threat 语义；采纳本决策不批准 `windows-platform-enablement` scope、PyInstaller 实现、发行资产或 EXE 发布。

## 决策

本 ADR 作出以下决策：

1. **唯一首版发行 profile**：Windows 首版 production profile 是 CPython 3.14 x64 上的 PyInstaller `--onedir --windowed`。installer、自动更新、签名、商店分发和 Windows ARM64 不由本 ADR 批准；`--onefile` 的临时 extraction root、更新、DLL/source identity 与恢复边界必须由新 ADR 批准，不能作为本 profile 的参数变体。
2. **所有权分离**：`windows-platform-enablement` 拟拥有 Windows build spec、manifest/closure generator、项目级 bootstrap authority、bundle-root/source closure contract、打包时 Qt/data 的收集与相对布局，以及 clean-machine release gate。Core/Feature5/Qt/Parser 等 owner 继续拥有各自 Gate roots、source/fixture/data 内容合同、capability、DTO、资源选择和业务 journey；Windows build 只收集并布置 owner 声明的资源，不拥有或改写 Qt/data 的产品语义。
3. **唯一项目级 bootstrap authority 与完整 Boot TCB**：发行物只有一个项目级 `frozen_source_bootstrap` authority，但 trust boundary 是所有在该 authority 建立前执行或影响它的完整 Boot TCB，不等于单个 bootstrap 文件。Boot TCB 必须枚举并content-address：release-owned/customized PyInstaller native bootloader/executable、Python DLL、pre-authority runtime hooks、bootstrap自身、建立manifest/hash/import所必需的stdlib与`ctypes`/hash/manifest/import-loader代码、其native extension/DLL，以及获批Windows system DLL allowlist。外部release evidence绑定native entry之前无法runtime自证的bootloader/PE静态导入；native entry及之后的每个实际加载路径由下述policy与runtime attestation约束。漏项、版本/摘要漂移或pre-authority hidden import均使发行候选不可用。
4. **无 adapter 循环自证**：bootstrap 在 authority 建立前不得导入 platform adapter、capability host 或任一待验证项目模块；它只使用 Boot TCB 内绑定的最低层 Windows API。然而它必须满足 ADR-020 已采纳的逐组件 rooted containment、reparse 拒绝、retained-handle/live identity、share/threat model 与 fail-closed 不变量，不能用 pathname normalize、文件存在或 manifest digest 代替这些证明。
5. **native-entry DLL 搜索边界**：DLL policy不是Python-level bootstrap可以追溯补救的事实。release-owned native bootloader必须审计PE static imports/delay-load，确保process entry前只有获批KnownDLL/System32 trust；进入native entry后、首次加载Python DLL或任何其他非KnownDLL之前，先用Windows loader policy排除CWD/`PATH`/未声明application目录，逐组件绑定无reparse的bundle/native directory，再以受限绝对路径及获批`LoadLibraryExW` search flags加载manifest中摘要锁定的Python DLL。其后只允许已验证bundle native directories与明确版本化的Windows system DLL allowlist；每个非系统native DLL必须属于Boot TCB/manifest，并在加载后核对实际module path/identity。Python `frozen_source_bootstrap`只消费native bootloader移交的不可伪造bundle/DLL attestation并继续source/fixture证明，不能声称自己保护了entry前load。若upstream bootloader无法满足该时序，W3 spike必须失败并改用获批custom bootloader/launcher，不能现场修补。
6. **bootstrap-owned `TrustedSourceLoader`**：能力关键 module 由 bootstrap 注册并拥有的 `TrustedSourceLoader` 执行；它可实现 `importlib.abc.SourceLoader` 或受控继承 `SourceFileLoader`，但必须从 bootstrap 保留并验证的 source handle 读取 exact bytes，核对 manifest digest 后直接交给 `source_to_code`/`compile`。不得重新按 pathname 打开执行内容，不得读写 `.pyc`/`__pycache__`，并必须拒绝 PYZ、bytecode 或其他 finder/loader 提供的同名 duplicate。code filename、`__file__` 与 `spec.origin` 是诊断投影，不是 authority。
7. **loader attestation 与 capability host**：`TrustedSourceLoader` 为每个已执行 module 产生不可序列化 attestation，绑定 bundle authority、manifest entry、retained-handle live identity、exact source digest、compiled code filename 与 loader instance/profile identity。`__file__`、`spec.origin`、loader path 与 code filename 必须一致投影 manifest 的 bundle-relative `.py`，但这些 metadata 只用于一致性反例；capability host 必须验证 source digest 和 loader attestation，再结合 owning Gate closure 铸造 capability，metadata 匹配本身不充分。
8. **source-only execution closure**：能力关键 modules 使用 PyInstaller documented source collection 或等价获批机制落为真实 `.py`，并从 PYZ/bytecode execution collection 排除；post-build 和 runtime 都必须证明没有可抢先执行的 duplicate module。真实 `.py`、Gate fixtures、TM/termbase seed data、产品 logo/icon/version metadata、Qt platform/image/icon/style plugins 及 owner manifest 指定资源保持约定 relative layout；`qwindows.dll` 位于 Qt 预期 bundle 目录，所有 runtime path 来自 bootstrap authority。
9. **clean、tracked、content-addressed production build**：production build 只能从 clean tracked source tree 生成；任何 untracked/modified input、现场复制或 build-work fallback 都使 run 无效。build spec、hooks、closure generator、bootstrap、owner roots/manifests、locked wheels、PyInstaller/Python/PySide6/Qt 与其他 native runtime 输入都必须被版本/摘要锁定并写入 deterministic canonical build manifest；manifest 记录 repository commit、relative path/kind/reason 与 SHA-256，生成器解析 transitive module/fixture/data/dynamic-import closure，不能以手写 dist 列表作为第二真相源。
10. **最小可行性硬门**：完整 UI/TM 打包前先用固定、已摘要锁定的 Python/PyInstaller 输入构建最小 onedir/windowed spike，只包含完整 Boot TCB、一个 critical external module 与一个 fixture，验证 rooted authority、`TrustedSourceLoader`/attestation、exact executed bytes、无 PYZ/bytecode duplicate、固定 DLL 搜索、非仓库 CWD，以及 reparse/swap/manifest/source/native-DLL tamper fail closed。任一失败必须回到本 ADR 重新设计，不能以现场修补继续完整发行。
11. **构建与运行证据**：build exit 0 不等于可发布。release evidence 必须绑定 exact source commit、全部 content-addressed build inputs、manifest/dist inventory 与 SHA-256，并在无 checkout、非仓库 CWD、clean user configuration 下运行真实 Qt window、SQLite FTS5/trigram create/query/reopen、项目 save/reopen、TM activation/restart recovery、TMX import 及 Gate recomputation。
12. **fail-closed 与长期触发器**：missing/tampered source、fixture、manifest、Boot TCB/native DLL、loader/attestation mismatch、PYZ/bytecode duplicate、reparse/swap、bundle-root escape、仓库路径读取或 mandatory test skip 均使发行候选不可用；不得使用 frozen boolean、path-only proof、Gate bypass、mock capability 或 source-mode-only evidence 放行 EXE。bootstrap/source authority、Boot TCB、DLL allowlist、manifest schema、closure roots、collection mode、locked tool/runtime input、bundle layout 或新增 capability-critical source/fixture 时，必须重新生成闭包并运行完整发行门；改变 trust root/authority ownership 或改为 `--onefile` 需新 ADR。

## 长期约束

- frozen executable 只能消费 Core/Spec owner 发布的 Gate/source roots，不能从构建成功、文件存在或 UI 可启动反向铸造 capability。
- critical module 的被执行 bytes 必须就是 retained verified handle 读取并由 `TrustedSourceLoader` 编译的 bundle `.py`；“PYZ 执行 + data 中另存源码”或 metadata-only identity 不符合本 profile。
- bootstrap 是唯一项目级发行 authority，但完整 Boot TCB 才是 pre-authority trust boundary；所有成员、生成输入、embedded manifest digest 与 executable hash 由 release evidence 绑定，runtime 不声称自证。
- Python bootstrap不得声称追溯保护native entry前加载；PE import closure与首次Python DLL/非KnownDLL load的搜索策略属于release-owned native bootloader合同和最小spike硬门。
- dist 不读取 source checkout，不依赖开发机 venv、CWD、`PYTHONPATH` 或 Qt plugin path。发行验证中的现场 patch、文件补拷贝、能力 skip 均使该 run 无效。
- 本 ADR 不修改 ADR-009 的 Core evidence authority，不修改 ADR-011 的 UI/Controller frozen DTO，也不把 Windows build owner 提升为 Parser、TM、Project 或 Resource 业务 owner。

## 后果与权衡

该 profile 保留 LocalCAT 既有的 source/fixture identity 和 capability gate，而不为 frozen 环境创建弱化旁路；onedir 也让真实源码、Qt plugin 与数据闭包可检查、可复现。代价是发行物包含可读源码且体积更大，构建要维护 deterministic closure、完整 Boot TCB、custom loader 与 DLL allowlist，并必须在 clean Windows 环境运行完整业务 E2E。`--onefile` 与 installer 被有意延后。

## 备选方案

- **默认 PYZ + 旁置一份 `.py` data**：拒绝。被执行 code 与被验证 source 可能不是同一对象。
- **`pyz+py` 双份 collection**：拒绝，除非未来 ADR 用新的精确 binding proof 取代本 source-only contract。
- **frozen boolean 或禁用 Gate**：拒绝。会绕过 ADR-009 的 default-unavailable authority。
- **从 checkout/CWD 查找 source/fixture/resource**：拒绝。发行物不再自包含，clean-machine evidence 无效。
- **首版 `--onefile`**：拒绝作为本 profile。临时 extraction root、启动更新、DLL/source identity 与 recovery 需要新 ADR 的独立 trust/recovery 设计。
- **以签名 manifest 取代真实 source loader contract**：延期。它会改变 trust root 和 capability_host identity，需单独 ADR 与迁移/反例矩阵。

## 取代关系

- **取代**：None。本 ADR 与 ADR-009/ADR-011/ADR-020 相交但不取代：ADR-009 继续拥有 evidence/capability 发布，ADR-011 继续拥有 Feature 5/UI DTO、composition 与 Controller boundary，ADR-020 继续拥有 rooted/reparse/live-identity 与 publish 语义；本 ADR 只拥有 Windows frozen bootstrap authority/Boot TCB、trusted source loading、source closure、build composition、打包收集/布局和 release proof。
- **被取代于**：None
