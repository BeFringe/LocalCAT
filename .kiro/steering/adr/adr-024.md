# ADR-024：Windows 私有主体采用身份提供方无关的 token profile

- **状态**：已采纳
- **实施授权**：本ADR不单独授权runtime或业务实现；实现由已批准的`windows-platform-enablement` R/D/T及WA-06依赖图控制
- **日期**：2026-08-28
- **批准日期**：2026-08-28
- **决策 owner**：LocalCAT 项目 owner
- **关联 Spec**：`windows-platform-enablement`、`tm-storage-retrieval-index`；ADR-021、ADR-023

## 背景

ADR-021以当前process primary token的canonical `TokenUser` SID建立Windows私有对象owner，并要求standard/elevated正向和同SID low-integrity/restricted负向证明；该主体表示是Windows ACL、MIC与跨重启device-secret重新证明所必需的。ADR-021决策6与11同时把local、domain、AzureAD账户来源列为首版mandatory环境矩阵，使Windows source、TM恢复和最终发行必须取得企业身份基础设施才能完成。

LocalCAT不登录Azure AD/Microsoft Entra ID，不调用云端身份API，也不以账户provider、显示名、domain join状态或登录来源铸造authority。Windows已经把可执行授权事实签发到当前进程token；对LocalCAT而言，authority-relevant事实是token类型、canonical `TokenUser` SID、完整性/AppContainer状态和对exact security descriptor的实际访问结果。把身份提供方来源提升为阻断证据没有增加私有存储证明，却会让与产品目标无关的企业环境成为首版前置。

## 决策

1. **provider-agnostic主体**：ADR-021决策2的process primary-token `TokenUser` SID继续是唯一私有主体身份。runtime不得查询或按local/domain/Entra provider、账户显示名、UPN、domain join状态或localized name分流；相同canonical SID bytes按同一主体处理。
2. **结构化首版profile**：受支持的LocalCAT桌面进程必须取得`TokenPrimary`、有效canonical `TokenUser` SID、medium或high integrity、非AppContainer及ADR-023要求的exact ACL/MIC/`AccessCheck`事实。standard与UAC elevated进程若具有相同`TokenUser` SID，必须都能使用同一私有对象；thread impersonation不能改变process-primary主体。
3. **负向边界**：同SID low-integrity/restricted token必须不能取得write/delete；AppContainer、service/非交互运行形态、impersonation-only或无法取得必要token/session事实时保持`CAPABILITY_UNAVAILABLE`。这些结果按token/session结构证明，不要求搭建每种账户provider环境。
4. **证据矩阵收窄**：首版blocking evidence保留当前Windows本地环境中的standard/elevated正向、同SID low-integrity/restricted负向、thread impersonation不改变process-primary主体，以及owner/DACL/MIC/ACE/tamper/FileId/reparse/device-secret恢复反例。domain/Entra环境若可得可作为非阻断兼容性覆盖；缺少该环境不构成skip、NO-GO或不支持结论。
5. **来源不成为持久字段**：`WindowsPrivateProof`、device key、attestation、owner envelope、日志与UI error均不得新增identity-provider、domain或账户显示字段。SID digest、security descriptor digest与既有owner context边界保持不变。
6. **工具链正交**：编译器、Windows SDK、PowerShell与测试helper只属于相应构建/验证证据；它们不进入私有主体profile，也不能代替真实token/ACL/MIC行为。

## 长期约束

- Windows private authority按token facts与实际访问语义定义，不按身份提供方品牌或组织目录拓扑定义。
- 新增账户provider不需要ADR；改变支持的token type、integrity/AppContainer/service边界、SID比较、ACL/MIC或授权结果才需要重新治理。
- 非阻断provider覆盖可以发现企业策略兼容性问题，但不得反向改变canonical主体或把未取得特定企业账号环境升级为产品失败。
- ADR-021/023的exact owner、DACL、MIC、device-secret、持久proof与业务envelope边界继续有效。

## 后果与权衡

Windows首版不再依赖domain controller或Microsoft Entra租户即可完成private storage、TM激活和跨重启恢复验收，同时保留SID、ACL、MIC与实际OS访问证明。代价是首发证据不宣称覆盖每一种企业策略组合；若某个企业环境施加额外策略，其兼容性按相同token profile诊断，而不是增加provider专属authority分支。

## 备选方案

- **把AzureAD改名为Microsoft Entra ID后继续保持mandatory矩阵**：拒绝。名称更新不改变身份提供方与本地文件authority正交的事实。
- **只支持本地账户并显式拒绝domain/Entra**：拒绝。runtime算法本来只依赖SID/token facts，按provider拒绝会制造无关分支。
- **移除SID/ACL/MIC严格证明**：拒绝。设备密钥和跨重启私有资格仍需要真实Windows访问边界；本ADR只删除provider环境门，不削弱物理证明。

## 取代关系

- **取代**：ADR-021决策6与11中local/domain/AzureAD作为mandatory正向环境矩阵的要求；这两项其余standard/elevated、low/restricted、ACL/MIC/tamper/recovery反例继续有效。
- **补充**：澄清ADR-021决策2的canonical `TokenUser` SID是identity-provider-agnostic，不改变该决策的主体owner。
- **被取代于**：None
