# ADR-026：按 owner 语义完成发布与 Parser 无状态 canonical writer

- **状态**：已采纳
- **实施授权**：本 ADR 不单独授权 runtime；实施由同步修订后的 owning Spec R/D/T 控制
- **日期**：2026-08-29
- **批准日期**：2026-08-29
- **决策 owner**：LocalCAT 项目 owner
- **关联 Spec**：`parser-subsystem-extraction` WA-01、`windows-platform-enablement`；ADR-015、ADR-020、ADR-023、ADR-025

## 背景

ADR-020 把 Parser、Chunk、Project、Resource、TMX 与 TM 统一接到 backend-neutral rooted/lock/publisher 边界是正确的，但其背景与决策 9 把这些 consumer 各自不同的发布协议概括为统一的“owner journal/LKG arm → durable state-machine commit”。这一概括不符合获批 Windows 改造前的 Parser 合同：`b925b80` 的 Parser canonical writer 只发布一个目标文件，在同一操作内完成 rooted candidate write/fsync、原子替换、实际目标回读与 `WriteReceipt`，没有 Parser journal、LKG 或跨进程恢复状态。

Project、Resource、Chunk、TM 及其他已由 owning Spec 明确声明冷恢复的 owner，确实需要 journal/LKG、generation、receipt ledger 或等价持久状态来协调多个 durable facts。共享平台 publisher 只能提供共同物理原语，不能反向要求所有 consumer 采用最强 owner 状态机。WA-01 曾按 ADR-020 的概括把 journal/LKG 无条件加入 Parser，这会把 Windows parity 迁移扩张为新的 Parser 持久子系统。

## 决策

1. **共享物理协议不统一业务状态机**：`BoundDirectoryPublisher` / `PendingPublication` 继续提供 candidate flush、handle-bound naming、candidate close、retained destination readback 与低层失败事实；每个 owning Spec 按其既有业务语义决定 publication 前置和成功终态。消费共享 publisher 不自动产生 journal、LKG、generation、ledger 或跨进程 recovery 责任。
2. **Parser canonical writer 保持无状态**：Parser 单文件 writer 的顺序固定为 rooted target-parent binding、获批 publish mode、candidate write/content flush、handle-bound rename、final facts capture、关闭 candidate handles、retained destination exact bytes/digest readback、terminal reproof，随后才签发 `WriteReceipt`。Parser 不创建 journal/LKG、持久 operation record 或 cold-recovery authority。
3. **Parser 失败语义**：publication 前失败必须证明原目标未变；publication 后若 actual destination、readback 或 terminal proof 无法闭合，返回稳定失败且不签发成功 receipt。进程终止验证只允许目标为完整 old 或完整 new；遗留随机 candidate 不构成 authority，不得按名称扫描后自动采信、恢复或删除。该合同不承诺 fresh process 自动完成或回滚一次中断的 Parser write。
4. **状态型 owner 保持不变**：Project、Resource、Chunk、TM 以及任何已由 adopted ADR/owning Spec 明确要求多事实 durable commit 或 cold recovery 的 owner，继续保有其 journal/LKG、generation、receipt、pending inventory 与恢复分类。本 ADR 不删除或弱化这些既有业务合同，也不把它们迁入 Parser 或平台层。
5. **重启证据按 owner 合同解释**：Parser 的 process termination、应用重启或正常 OS reboot 场景只复核既有完整目标与“无虚假 receipt”，不要求恢复 Parser operation state。需要 cold recovery 的 owner 继续按自身合同执行 restart/reboot reproof。本 ADR 不改变 ADR-025 对正常 OS reboot 与 forced-power-loss 的分层。
6. **POSIX/Windows 对称**：Windows Parser 保持 `b925b80` POSIX writer 的单文件、跨进程无状态业务模型，同时以 Windows rooted/publish backend替换不可用的 POSIX primitive；平台差异不得成为新增 Parser 持久 schema 的理由。

## 长期约束

- 只有 owning Spec 或已采纳 ADR 明确声明跨进程恢复时，consumer 才能被要求建立持久 journal/LKG 或等价 operation state。
- `PendingPublication` 是物理发布握手，不是共同业务 journal，也不铸造业务 success。
- “完整 old/new”与“old/new/recovery-only”是不同合同：无状态单文件 writer 不得被要求虚构 recovery-only 状态；状态型 owner 不得用无状态 writer 的较窄语义替代自身恢复责任。
- source、frozen 与 packaged composition 对同一 owner 使用同一业务状态模型；打包形态不反向新增 Parser recovery authority。

## 后果与权衡

Windows Parser 可在不新增持久格式和冷恢复状态机的情况下取得与既有 POSIX writer 等价的 rooted publication、readback 与 receipt 语义，避免平台迁移阻塞于无产品需求的 Parser journal。代价是进程在候选创建后异常终止可能留下无权威临时文件，或在替换完成但 receipt 返回前留下完整新目标；后续操作不能通过扫描文件名猜测或自动清理这些事实。

状态型 Project/Resource/Chunk/TM owner 的持久恢复能力不变，仍承担其既有多阶段事务复杂度。

## 备选方案

- **所有 publisher consumer 统一 journal/LKG**：拒绝。它把平台物理原语提升为共同业务状态机，并给原本无状态的 Parser 增加持久 schema、恢复和清理责任。
- **Parser 复用 Project/Resource journal**：拒绝。会产生反向依赖和第二业务 authority，且不同 owner 的 identity、receipt 与恢复决策不可互换。
- **只修改 WA-01，不修正 ADR-020**：拒绝。ADR-020 决策 9 仍会驱动后续 Spec 或 reviewer 重新引入同一外推，留下长期治理冲突。
- **取消 retained readback/terminal reproof**：拒绝。无状态不等于弱化成功证明；Parser 仍须在同一操作内证明实际发布字节后才签发 receipt。

## 取代关系

- **取代**：ADR-020 背景中把 journal/LKG 视为所有列举 consumer 的共同既有事实，以及决策 9 对所有 publisher consumer 无条件要求“owner journal/LKG arm”和“durable state-machine commit”的部分；其 rooted authority、lock、publish mode、handle lifecycle、readback、POSIX parity与 fail-closed 边界继续有效。补充 ADR-025 决策 1～3 对无状态 Parser owner finalization/reboot evidence 的解释，不改变其 Windows documented publish 或硬断电分层。
- **被取代于**：None
