# ADR-032：分离导出目录准备与文件发布

- **状态**：已采纳
- **日期**：2026-10-10
- **决策 owner**：LocalCAT 项目 owner
- **关联 Spec**：`windows-platform-enablement`、`rpy-project-codec`

## 背景

目录创建接口与取得目录句柄是不同操作。创建调用成功不能证明随后绑定的对象仍是创建者；首次身份捕获之后的复证不能补回该连续性。普通导出需要在现有支持平台上保留嵌套路径，同时不把无法证明的创建者身份当作文件发布权威。

## 决策

1. 输出父目录全部存在时，保持只读预览和一次明确确认后的逐文件发布。预览按完整相对路径区分新建与覆盖，存在覆盖项时确认操作明确包含覆盖；不因目标位于原目录而一律拒绝。
2. 输出父目录缺失时，先只读准备全部候选和目录计划。用户可明确确认仅准备缺失目录；该操作不写 TL、不签发文件发布目标绑定。
3. 目录准备逐组件使用输出根内 no-follow、已复证的当前目录，拒绝逸出、符号链接及已观察身份漂移。创建调用成功和其后当前目录绑定是两类事实，不声明不可替换的创建者连续性，也不把该目录绑定称为本批创建者权威。
4. 目录准备结束后，一律关闭并丢弃旧计划及其目录句柄。新的只读预览重新验证全部候选与目标条件，并将当前存在的祖先绑定为 retained authority。用户确认该新预览后才可发布文件；不得自动沿旧确认继续。
5. 目录准备准确报告创建调用成功、失败和结果无法确定的路径，不承诺空目录回滚。文件发布继续沿用 Parser prepared write、rooted target binding 与逐文件结果；取消、过期或关窗不触发后续阶段。

## 长期约束

平台拥有目录原语与受控绑定，Application 拥有阶段、会话和确认，Qt 仅消费中立投影。目录准备结果、包内私有成员和历史路径均不能签发文件发布权威。新预览之后的存在／不存在与身份条件不得被重新绑定为最新状态。

## 后果与权衡

缺失目录时增加一次用户确认，换取平台可证明的文件发布起点。已有目录的导出交互保持不变；准备操作可能留下空目录，产品如实展示。

## 备选方案

- 一次确认并把创建之后首次捕获作为保证起点：交互较短，但会收窄创建前竞争检测保证，未默认采用。
- 改用原子创建并返回目录句柄的其他 native API：需要独立资格及平台范围决策，不能解决当前全部支持平台。
- 仅导出已有目录：保持现合同的一部分，但不能独立完成保留嵌套路径的用户旅程。
