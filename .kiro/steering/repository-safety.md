# 仓库连续性与工作树安全

本文件约束所有 LocalCAT 分支、Kiro Spec 和多 Agent 工作树。目标是让任一开发阶段都能从 Git 提交恢复，而不是依赖某个进程、对话或临时目录。

## 强制规则

1. **活动 worktree 必须持久化**
   - 唯一工作副本不得位于 `/tmp`、tmpfs、容器临时层或会被系统清理的缓存目录。
   - 新增长期工作树前先确认目标挂载类型和路径；Feature 5 工作树应位于用户选择的持久目录，不在项目文档中固化机器相关绝对路径。
   - `git worktree prune` 只能清理失效元数据，不能被当作内容恢复手段。

2. **Spec 与 Steering 必须进入 Git**
   - `.kiro/` 是需求、设计、任务、裁决和项目事实的权威持久来源，不得被 `.gitignore` 排除。
   - `AGENTS.md` 和项目自带的 `.opencode/skills/kiro-*` 工作流也应由 Git 跟踪；`.opencode` 的运行时依赖、缓存和 `node_modules` 继续忽略。
   - 新建或批准一个 Spec 阶段后，应在进入下一阶段前形成可恢复提交。
   - 对话摘要、Agent 内存和未提交 worktree 只能作为临时上下文，不能成为唯一权威。
   - “解除忽略”只代表文件具备被跟踪资格，不代表可以整目录无差别暂存。禁止用 `git add .kiro`、`git add .opencode` 或等价通配操作一次吸收来源和所有权不同的文件。

3. **可见性不等于所有权**
   - Git worktree 检出的是分支上的完整仓库；Feature 5 工作树看到 Qt、Parser 或未来规格属于正常可见性，不表示 Feature 5 可以修改或提交它们。
   - 每条开发线只能修改其在 `spec-ownership.md` 中拥有的 Spec。跨线契约、路线图和安全规则必须形成单独的共享治理提交。
   - 共享变更只允许在一个分支形成一次提交，其他活动分支通过 merge/rebase 继承同一历史；禁止在不同 worktree 中分别应用并提交等价补丁。
   - cherry-pick 只用于有明确理由、可追踪来源的 backport，不作为活动垂直线之间的常规同步方式。
   - `.kiro/settings/**` 与 `.opencode/skills/kiro-*` 是项目级 SDD 基础设施，不得混入 Feature 5 或 Qt 功能提交；升级时必须记录工具版本、安装命令和差异审阅结果。

4. **任务状态必须有证据**
   - 只有实现、自动化验证和设计对照均完成后，才能把对应可执行任务从 `[ ]` 改为 `[x]`。
   - 任务勾选优先与对应代码、测试和必要文档放在同一个语义提交；跨多个提交的任务在最终验收提交中勾选。
   - 不为每个机械步骤制造提交；以可独立审查、可独立回退的任务或紧密任务组为粒度。

5. **分支与工作树启用前检查**
   - 确认工作树路径、分支唯一占用、共同基线、未提交状态和目标文件系统。
   - 多 Agent 并行前明确每条线的文件/边界所有权；共享契约先形成提交，再由各分支消费。
   - Feature 5 可以继承最新已验收 UI 基线，但自身提交不得修改 Qt 所有权范围；Core 内部实现也不得反向成为 Qt 的第二权威。

6. **凭据不得进入 Git 元数据或输出**
   - remote URL、配置、日志和诊断输出不得包含访问令牌或其他凭据。
   - 发现已暴露凭据时应停止 push，撤销或轮换凭据，并改用不含秘密的 remote 配置。

## 最小检查点

每次阶段切换前至少确认：

- `git status` 中没有被忽略的唯一 Spec；
- 当前阶段文件已由 `git ls-files` 覆盖或已明确加入本次提交；
- 暂存区只包含本次任务的显式文件清单，并已用 `git diff --cached --name-status` 复核来源和所有权；
- 活动分支之间没有本应通过 merge/rebase 继承的 patch-equivalent 重复提交；
- 已完成任务的 `[x]` 与验证证据一致；
- 活动 worktree 路径位于持久文件系统；
- 下一条垂直线可以仅凭仓库内容恢复上下文。
