# 仓库连续性与工作树安全

本文件约束所有 LocalCAT 分支、Kiro Spec 和多 Agent 工作树。目标是让任一开发阶段都能从 Git 提交恢复，而不是依赖某个进程、对话或临时目录。

## 强制规则

1. **活动 worktree 必须持久化**
   - 唯一工作副本不得位于 `/tmp`、tmpfs、容器临时层或会被系统清理的缓存目录。
   - 新增长期工作树前先确认目标挂载类型和路径；Feature 5 工作树应位于用户选择的持久目录，不在项目文档中固化机器相关绝对路径。
   - `git worktree prune` 只能清理失效元数据，不能被当作内容恢复手段。

2. **Spec 与 Steering 必须进入 Git**
   - `.kiro/` 是需求、设计、任务、裁决和项目事实的权威持久来源，不得被 `.gitignore` 排除。
   - `AGENTS.md` 和项目自带的 `.opencode/skills/kiro-*` 工作流也应由 Git 跟踪；`.opencode` 的运行时依赖、缓存和 `node_modules` 继续忽略。
   - 新建或批准一个 Spec 阶段后，应在进入下一阶段前形成可恢复提交。
   - 对话摘要、Agent 内存和未提交 worktree 只能作为临时上下文，不能成为唯一权威。
   - “解除忽略”只代表文件具备被跟踪资格，不代表可以整目录无差别暂存。禁止用 `git add .kiro`、`git add .opencode` 或等价通配操作一次吸收来源和所有权不同的文件。

3. **可见性不等于所有权**
   - Git worktree 检出的是分支上的完整仓库；Feature 5 工作树看到 Qt、Parser 或未来规格属于正常可见性，不表示 Feature 5 可以修改或提交它们。
   - 每条开发线只能修改其在 `spec-ownership.md` 中拥有的 Spec。跨线契约、路线图和安全规则必须形成单独的共享治理提交。
   - 治理分支仅承载共享治理基线及其治理提交，不吸收开发提交栈；治理补丁形成唯一提交后，获准重放的开发区间 rebase 到治理 tip 之后。不得为避开集成而把治理分支前移到最新开发 tip，再追加治理提交。具体操作遵循下节“治理集成与受控重放”；分支名由 Agent 按工作分配。
   - cherry-pick 只用于有明确理由、可追踪来源的 backport，不作为活动垂直线之间的常规同步方式。
   - `.kiro/settings/**` 与 `.opencode/skills/kiro-*` 是项目级 SDD 基础设施，不得混入 Feature 5 或 Qt 功能提交；升级时必须记录工具版本、安装命令和差异审阅结果。

4. **任务状态必须有证据**
   - 只有实现、自动化验证和设计对照均完成后，才能把对应可执行任务从 `[ ]` 改为 `[x]`。
   - 任务勾选优先与对应代码、测试和必要文档放在同一个语义提交；跨多个提交的任务在最终验收提交中勾选。
   - 不为每个机械步骤制造提交；以可独立审查、可独立回退的任务或紧密任务组为粒度。

5. **分支与工作树启用前检查**
   - 确认工作树路径、分支唯一占用、共同基线、未提交状态和目标文件系统。
   - 多 Agent 并行前明确每条线的文件/边界所有权；共享契约先形成提交，再由各分支消费。
   - Feature 5 可以继承最新已验收 UI 基线，但自身提交不得修改 Qt 所有权范围；Core 内部实现也不得反向成为 Qt 的第二权威。

6. **凭据不得进入 Git 元数据或输出**
   - remote URL、配置、日志和诊断输出不得包含访问令牌或其他凭据。
   - 发现已暴露凭据时应停止 push，撤销或轮换凭据，并改用不含秘密的 remote 配置。

## 治理集成与受控重放

1. **先确定基线和范围**：核实共同治理基线、现有治理 tip、各开发 tip 和预期远端 tip 的完整对象 ID；列明允许重放区间（不含下界、包含上界）及明确不动的保护锚点。批准 ADR、修改文档或修正提交消息，不自动授权跨越冻结的评审、验收、发布或分叉历史。若既有锚点使治理前移无法在已授权区间内完成，先给出确切影响范围并取得跨越授权，不改为在开发 tip 后追加治理。
2. **先保全原链**：任何已发布历史重排前，核实所选稳定引用能够到达原治理、开发、待集成规格和受保护提交；先推送该引用，再从远端验证其目标对象。只有本地 reflog、未推送分支或口头说明不算保全。原链及旧报告保留原 SHA 和原验收范围，重放提交不得被说成原候选重新通过。
3. **协调工作树**：通过 `git worktree list` 核对分支占用、HEAD 和未提交内容，确认相关执行者不在并发写入。脏工作树不被 reset、覆盖或自动 stash；不属本轮范围的 source、历史技术路线和证据工作树保持原位，后续迁移另按其授权处理。不得仅为移动分支而丢弃它们的状态。
4. **治理与开发分离集成**：治理分支从已核实的共享治理基线续接，只包含治理路径的有效变化；owner 规格和实现保留各自语义提交，由开发栈在允许区间内 rebase 继承治理 tip。不得复制等价治理补丁到不同活动分支；不以 merge 把开发栈倒灌进治理分支。待集成临时分支仅在有效变更全部可从实际分支恢复后删除。
5. **核对提交和文件**：重排前后使用提交映射、`range-diff` 和最终 tree/file diff 核查顺序、遗漏、重复与冲突处理。纯父节点或消息变化应保持对应文件内容；审批登记、引用修正或其他有效变化须逐项说明。只修正本次集成必需的活动引用，不批量替换历史报告的 SHA，也不借 rebase 清理全库 evidence。纯 Git 元数据变化不自动触发全量产品重验；真实代码、输入、合同或运行时变化按 owner 触发验证。
6. **受控发布与继续开发**：更新已有远端指针时，使用明确预期对象 ID 的 `--force-with-lease=<ref>:<expected>`；实际远端不符就停止核查，不覆盖他人的更新。推送后再次核对治理指针、开发继承关系及保留引用。以整理后的实际开发分支 HEAD 继续工作，不固定退回旧修复 SHA。

上述核查只需要本次操作的可恢复材料和 Git 引用，不另建永久追溯台账。与当前集成无关的摘要文件、证据依赖和历史清理应另行形成具体消费者与替代方案的结论，经批准后处理。

## 提交消息

- `scope` 表示实际作用域，例如共享规则/ADR 为 `governance`，Core 为 `core`，UI 为 `ui`，平台组合为 `platform`；不以工作机器、临时分支或任务编号代替作用域。
- `description` 直接说明有效变更；一个提交对应完整、可审查的能力或合同修改，不记录批准对话、试错流水、重复验收摘要或可直接从 diff 得到的核验计数。
- 返工可在获准重放区间内按完整能力整合；消息规范化同样不得越过保护锚点，不能借改名扩张历史重排范围。

## 最小检查点

每次阶段切换前至少确认：

- `git status` 中没有被忽略的唯一 Spec；
- 当前阶段文件已由 `git ls-files` 覆盖或已明确加入本次提交；
- 暂存区只包含本次任务的显式文件清单，并已用 `git diff --cached --name-status` 复核来源和所有权；
- 活动分支之间没有本应通过 merge/rebase 继承的 patch-equivalent 重复提交；
- 治理集成的基线、允许重放区间、保护锚点、远端保留引用与精确 lease 均已核实；
- 已完成任务的 `[x]` 与验证证据一致；
- 活动 worktree 路径位于持久文件系统；
- 下一条垂直线可以仅凭仓库内容恢复上下文。
